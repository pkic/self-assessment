# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

`@pkic/self-assessment` is a **self-contained web component** (a UMD bundle, not an SPA) that embeds the PKI Consortium's PKI Maturity Model (PKIMM) self-assessment into any HTML page via a `<self-assessment>` custom element. Consumers load `dist/self-assessment.js` and drop the tag in their page — zero-config: the latest PKIMM model and the references catalog are bundled into the JS, so `<self-assessment>` renders with no attributes at all. A host may still override the data source via URLs supplied as attributes (`dataUrl`, `referencesUrl`). Extensions are **browser-managed** — the user uploads and removes them in the Extensions tab (persisted locally in IndexedDB); there is no `extensionsUrl` attribute and no extension is ever fetched from the network.

Because it is embedded in arbitrary host pages, design decisions revolve around isolation and theming: CSS class names are intentionally **un-hashed** but namespaced with a `pkimm-` prefix, and visual tokens are exposed as `--pkimm-*` CSS custom properties that hosts may override.

## Commands

Node version is pinned via `.node-version` to an **exact** patch (currently 24.15.0). Two constraints drive it: jest 30 needs Node ≥24.9 to load the ESM `@react-pdf/renderer` in the real-render PDF tests, but the test harness's `pdf-parse` (2017-era bundled pdf.js) throws at module init on 24.18.0 — so the patch is pinned to a validated version rather than a floating `24`. Bump it deliberately, re-running the full suite.

npm run build        # production UMD build → dist/self-assessment.js

The dev page (`src/public/index.html`) is attribute-free and zero-config — it renders against the bundled model + references with nothing else in `dist/`. Copy the runtime YAML files (`src/public/pkimm-model-*.yaml`, `src/public/pkimm-references.yaml`) into `dist/` only if you want to exercise the `dataUrl`/`referencesUrl` override path locally; CI still does this with explicit `cp` steps after `npm run build` regardless.

## Architecture

### Entry path

`src/index.tsx` → `src/SelfAssessmentComponent.tsx` (defines the `<self-assessment>` Custom Element, reads the `dataUrl`/`referencesUrl`/`modes` attributes, mounts via React 19 `createRoot`) → `src/App.tsx` → `src/components/Assessment/Assessment.tsx`. The `modes` attribute (parsed by `src/utils/parseModes` → `parseModes`) gates which assessment views are offered: unset (or empty/unknown) enables both Self and Full with Self as the default view; `modes="self"` disables Full; `modes="full"` keeps Self available (it can never be disabled — the raw data must stay visible to the host) but defaults the view to Full. It is comma-list tolerant and case-insensitive.

Webpack outputs UMD with `library: "SelfAssessment"`. The bundle registers the custom element on import, so consumers just `<script src=…>` it.

### Where the state lives

`Assessment.tsx` is the workhorse component and owns all mutable widget state. Persistence and shape changed substantially in 2.0.0:

- **IndexedDB `pkimm-sa`** (structural version pinned at 1 forever; records carry `stateSchemaVersion`) holds the `SavedState`: one record per assessment plus a `meta` store (`activeId`, display order, per-assessment `lastExport:` timestamps) and a `revisions` ring buffer (max 20/assessment, ordered by a monotonic `seq`: `pre-migration`, `pre-restore`, `pre-import` (snapshotted before a v2-import Replace overwrites a same-id local copy), 30-minute `timer` snapshots of changed assessments). Access goes through the async `StorageAdapter` seam (`src/utils/storageTypes.ts` + `storageAdapter.ts`, singleton via `getStorageAdapter()`; in-memory fallback when IndexedDB is unavailable — single-tab semantics, no locks/broadcast). **Writes are merge-on-write:** never delete by absence (explicit `deleteIds` only), never overwrite a record whose stored `meta.updatedAt` is newer — cross-tab safe. Deleting an assessment also purges all of its `revisions` (no snapshot outlives its parent, and `restoreRevision` on a purged id fails cleanly) and records a tombstone (`meta` key `deletions`, pruned after 90 days) so a stale full-array flush from another tab can't resurrect it; a legitimately newer write for the same id still clears its tombstone. The in-memory fallback purges revisions on delete too but skips tombstones — it's single-tab, so nothing can flush a stale copy behind its back. **localStorage["pkimm-sa"] is now read-only legacy**: imported into IndexedDB exactly once (marker `pkimm-sa-idb-imported`), never written or deleted — a host rolling back to widget 2.0.0 still sees its pre-upgrade data. Cross-tab sync is Web Locks (`pkimm-sa-write`, per-assessment edit locks `pkimm-sa-edit-<id>`) + BroadcastChannel (`pkimm-sa`) — the old `storage`-event listener is gone. Writes are debounced 300 ms and force-flushed (best-effort) on `visibilitychange: hidden`/`pagehide`. Durability: `navigator.storage.persist()` after the first successful write; save-status chip + export nudges + storage-estimate footer driven by `src/utils/{durability,saveStatus}.ts`.
- **localStorage["assessmentData"]** is the legacy 1.0.0 key. The widget detects it non-destructively and offers the user a one-time prompt to import or keep separate; it is never written to anymore, never auto-deleted.
- **URL hash** (`generateURL` / `decodeProgressHash` in `src/utils/urlGenerator.ts`) carries `stateSchemaVersion`, `dataVersion`, `progress`, `enabledExtensions[]`, and the three name fields. Hashes from the released 1.0.0 widget (no version fields) still decode as a `dataVersion: "1.0.0"` payload. Progress in the hash is **compacted** to `{ level, applicability }` per category (drops `result` and `description` because both are derivable). For a full (requirement-level) assessment the compacted `level` is the **effective** (requirement-derived) category level and `applicability` is `false` whenever that effective level is Not Applicable — explicit _or_ derived (`eff.display === -1`), not the stored category flag — so a widget that only reads `progress` still renders a correct category-level view. A full assessment additionally carries a **`full` param**: the per-requirement ratings (`level`/`applicability` only — notes/evidence/rationale never travel), JSON-serialized, deflate-compressed via `fflate` (`deflateSync`/`inflateSync`, raw DEFLATE — there is no `deflateRawSync` in fflate) and base64-packed through dedicated binary-safe helpers (`bytesToBase64`/`base64ToBytes`, distinct from the text-only `utf8ToBase64`), tagged `hashVersion: 2`. The codec is **synchronous** (`generateURL` is called in render). `decodeProgressHash` reads the `full` param back (synthesizing empty notes/evidence) and `decodeFullParam` **never throws** — on a malformed or non-`hashVersion:2` param it returns null, so a released widget simply ignores `full` and reads the compact `progress`. A **quick** assessment (no requirement ratings) emits no `full` param and its `progress` bytes are unchanged — quick-share links stay byte-identical to before (pinned by an exact-string test). The load effect in `Assessment.tsx` re-hydrates the full ProgressData from the source YAML before placing the transient assessment into state; the transient also carries the decoded `requirementProgress`. A fully-populated 2.0.0 full-assessment URL measures ~3.2 KB — above the Share modal's `QR_URL_LIMIT` (2900), so such links render the text-only fallback rather than a QR (pinned by the §11 acceptance test). The persisted store (IndexedDB `pkimm-sa`) and exported YAML stay in the full shape — the URL stays compact plus the compressed `full` param.
- **QR code**: the Share modal renders the URL as a 200 px SVG QR (`qrcode.react`); the self and extension PDF reports embed a 140 px PNG QR on the cover page (`qrcode` library, error correction level M), gracefully falling back to text when the URL exceeds the ~2.9 KB QR upper bound. The full-tier reports (Attestation/Assessment/Detailed/Custom) stamp `showShareLink: false` and omit the QR/share link entirely — a full assessment's richest content doesn't fit in a share link.

A URL hash always renders as a **transient assessment** (id prefixed `transient-`); it lives in memory only, never auto-persists, and the `TransientAssessmentBanner` gives the user explicit Save/Discard.

Progress keys:

- Core categories: `${moduleId}.${categoryId}` (2.0.0 uses kebab ids, e.g. `G.strategy-and-vision`; 1.0.0 used positional `G.1`).
- Core requirements: `${moduleId}.${categoryId}.${requirementId}`.
- Extension-scoped entries: `${extensionId}.${moduleId}.${categoryId}`.

The four core modules are fixed and validated by the JSON schema: G (Governance), M (Management), O (Operations), R (Resources).

### Vendored schemas and YAMLs (`src/public/`)

Built-in schemas are imported by `yamlParser.ts` and inlined into the bundle by webpack.

- `pkimm-model.schema-1.0.0.json` (draft-07), `pkimm-model.schema-2.0.0.json` (draft-07)
- `pkimm-references.schema-1.0.0.json` (draft-07)
- `extension.schema-1.0.0.json` (draft 2020-12)
- `pkimm-model-1.0.0.yaml`, `pkimm-model-2.0.0.yaml`, `pkimm-references.yaml`

Two Ajv instances handle the mixed drafts — `Ajv` for draft-07 and `Ajv2020` for the extension schema. `yamlParser.validateSchema` dispatches via a `${kind}:${schemaVersion}` key.

**Bundled defaults.** `src/public/*.yaml` (the three files above) are the single source for two consumers: `src/defaults/bundledData.ts` imports each as a raw string via a webpack `asset/source` rule (jest mirrors this with a `.yaml` raw-transform, `src/test-utils/yamlTransform.js`, plus the ambient `declare module "*.yaml"` in `src/yaml.d.ts`), and the deploy workflows still copy the same files to gh-pages (see CI section below). `getBundledModelYaml(version)` looks up either bundled model version; `DEFAULT_MODEL_VERSION` (`"2.0.0"`) is what a no-`dataUrl` load resolves to, and `BUNDLED_REFERENCES_YAML` is what a no-`referencesUrl` load resolves to. Both `dataUrl` and `referencesUrl` remain optional overrides — setting either attribute still fetches from that URL, unchanged. The bundled 1.0.0 model is archival: nothing on the default path loads it, it exists so a saved 1.0.0 assessment still has 1.0.0 fixtures to migrate from. `getBundledModelYaml` is internal — it is not re-exported from the UMD entry point (`src/index.tsx`), so this is not a public API addition.

### Schema-aware parser (`src/utils/yamlParser.ts`)

`yamlParser` discriminates between `AssessmentData` (`modules`), `ExtensionData` (`extension`), and `ReferencesCatalog` (`references` without `modules`) by sniffing top-level keys. `validateSchema` is a separate exported helper; model/extension/references each go to their respective compiled Ajv validator. Unknown schemaVersion throws a clear "upgrade the widget" error.

### Migration engine (`src/utils/stateMigration.ts`)

Pure function `migrate(source: Assessment, target: AssessmentData, loadedExtensions?: ExtensionData[]): MigrationResult` maps a saved assessment's progress to a different version's category/requirement ids by **name**, using the assessment's `sourceStructure.byKey` snapshot. Cases handled:

- Core categories/requirements: matched by `${moduleId}|${normalize(categoryName)}` and, for requirements, by description.
- Extension-scoped entries: same lookup, prefixed with the extension id; version bumps update the corresponding `enabledExtensions[]` record. The `{moduleId, categoryName}` needed for the name-match comes from `sourceStructure.extensionScopes[oldKey]` when present, but that map is **never populated in production** (`buildStructureSnapshot` only snapshots the core model), so `migrate` **derives** the scope from data it already has: it identifies an extension entry by matching the key against the assessment's own `enabledExtensions` (longest matching id wins, so a dotted/prefix id can't misclassify), strips the extension id to the core-category key (e.g. `pqc.G.1` → `G.1`), and resolves `{moduleId, categoryName}` from the same `byKey` snapshot the core loop uses. A core key already present in `byKey` is never reprocessed here (guards a pathological extension id that shadows a module letter). Without this derivation, extension progress — level and the category-grain notes/evidence/workspace fields alike — was silently dropped on every migration.
- Extensions referenced by saved progress but not loaded on this page, or an extension entry whose scope can't be resolved: progress is preserved at the original key (migration never silently drops assessed data).
- Whitespace/case differences in names are tolerated; the legacy 1.0.0 typo `"he scope of policies..."` is preserved verbatim so it surfaces as `unmappedFromSource` rather than silently matching the 2.0.0 corrected wording.

The migration summary (`mapped`, `addedInTarget`, `unmappedFromSource`, `reclassifiedLevel1ToZero`) drives the `MigrationSummary` modal.

### Legacy reclassification (`src/utils/legacyReclassify.ts`)

`reclassifyUntouchedLevelOne(progress, sourceData)` resets entries with `level === 1` and unchanged level-1 description text back to `level === 0` (Not Assessed). This is called only on legacy import, never on subsequent saves.

### Bundled legacy names (`src/legacy/pkimm-model-1.0.0-names.ts`)

A frozen JSON-like map from the released 1.0.0 widget's progress keys (`G.1`, `G.1.1`, …) to `{ moduleId, categoryName, requirementName? }`. Used by `storage.importLegacyData` to populate `sourceStructure.byKey` without re-fetching the 1.0.0 YAML.

### Storage helpers (`src/utils/storage.ts`)

- `readSavedState` / `writeSavedState` — typed access to `pkimm-sa`; throws if `stateSchemaVersion` is newer than the widget supports.
- `detectLegacyAssessmentData` — returns the parsed `assessmentData` payload only when `pkimm-sa` is absent (used by the first-load auto-prompt).
- `readLegacyAssessmentData` — returns the parsed payload without the first-load guard (used by the AssessmentManager's explicit "Import legacy" button, which fires even when `pkimm-sa` already exists).
- `importLegacyData` — turns a legacy payload into an `Assessment` with a `sourceStructure` populated from `PKIMM_1_0_0_NAMES`.
- `removeLegacyAssessmentData` — explicit user action only.
- `importYAMLFile` — the sole import path for assessment files. Rejects a JSON-envelope shape (`kind === "pkimm-assessment"` or a bare `formatVersion` field — the fingerprint of the removed `.pkimm.json` codec) with a clear "This looks like an older JSON assessment file, which is no longer supported. Re-export the assessment as YAML." error, so a stale file degrades loudly instead of being silently misparsed as a legacy blob (YAML is a JSON superset). Otherwise discriminates a new-shape export (has `dataVersion` + the new fields; lossless and id-preserving) from a legacy single-assessment YAML (`importLegacyData`, always mints a fresh id). A `stateSchemaVersion` newer than the widget supports throws `ForwardCompatError`.
- `importAssessmentFile(text)` — the never-throws entry point used by the Assessments tab's upload control and the Comparison panel's baseline upload. Calls `importYAMLFile` and reports the outcome via the `ParseResult` discriminated union (`{ ok: true, assessment, stateSchemaVersion } | { ok: false, error, forwardIncompatible? }`, defined in this file) so callers branch once whether the file parsed, was rejected as a JSON envelope, was malformed, or was forward-incompatible.
- `newEmptyAssessment(dataVersion, sourceStructure)` and `buildStructureSnapshot(data)`. `newEmptyAssessment` seeds level-0 progress entries for every core category, so the rest of the widget never sees a missing progress entry.
- Ids use `crypto.randomUUID()` with a `id-${Date.now()}-…` fallback for environments without the web standard.

### The lossless assessment export (YAML)

The single lossless, portable export of one assessment — the format to reach for when moving an assessment between browsers/hosts or backing it up — is **YAML**, produced by `buildYAMLExportPayload`/`exportToYAML`/`downloadAssessmentYAML` in `src/utils/urlGenerator.ts` and read back by `importYAMLFile` in `src/utils/storage.ts`. An earlier `.pkimm.json` JCS/JSON envelope codec (`src/utils/assessmentFile.ts`, `PkimmAssessmentFileV2`) shipped briefly and has since been **removed** — the YAML path now covers everything it did, plus the fields (`id`, `meta`, `lastView`, `lastPosition`) the old codec also carried.

- **`buildYAMLExportPayload`** is the pure payload builder (side-effect-free, so tests can pin its exact shape): it always includes `id`, `name`, `dataVersion`, `progress`, `enabledExtensions`, the three name fields, `sourceStructure`, `meta`, and (when present) `lastView`/`lastPosition` — the same identity/storage fields the old JSON envelope carried, so the export is a full, lossless snapshot of the assessment record, not just its content. It reuses **`hasV2Content(assessment)`** (`src/utils/stateSchema.ts`, unchanged) to decide whether to also spread in the v2-only fields — `requirementProgress`, the metadata scalars (`organizationName`, `assessorPosition`, `assessorCompany`, `assessmentType`, `startDate`, `targetDate`, `finishDate`), `pkiEnvironment`, `workspace`, `actionPlans` — stamping `stateSchemaVersion: 2` when any is present, else `1`. A truly-quick assessment (none of that content) takes the empty-spread branch and stamps `1`. The payload always carries `id`, `meta`, and `exportedAt` — fields the pre-v2 export didn't have — so a quick assessment's YAML is no longer byte-identical to that older output; v1 consumers and the migration engine are unaffected regardless, since both simply ignore unknown top-level keys (the current shape is still pinned by an exact-string test).
- **`downloadAssessmentYAML(assessment)`** maps a full `Assessment` onto the export payload and triggers the browser download — this is now the **only** download path in the widget; both the Report tab's action bar and the Assessments-tab manager call it (see the Tabs section below).
- **`importYAMLFile(text)`** (`src/utils/storage.ts`) is the sole import path. It first checks for the fingerprint of the removed JSON envelope (`kind === "pkimm-assessment"` or a bare `formatVersion` field) and **rejects it with a clear error** — "This looks like an older JSON assessment file, which is no longer supported. Re-export the assessment as YAML." — rather than silently misreading it as a legacy blob (YAML is a JSON superset of JSON, so a `.pkimm.json` file would otherwise parse as _something_). Otherwise it discriminates a new-shape export (has `dataVersion`) from a legacy 1.0.0 single-assessment YAML. A new-shape import is **lossless and id-preserving**: `id`, `meta`, `lastView`, `lastPosition`, and every v2 field round-trip field-for-field; a legacy import always mints a fresh id via `newId()` (no stable id to preserve). A `stateSchemaVersion` newer than `WIDGET_MAX_STATE_SCHEMA_VERSION` throws `ForwardCompatError`. The result is run through `normalizeAssessmentActionPlans` so action plans are always current-shaped regardless of when the file was exported.
- **`importAssessmentFile(text)`** (also `storage.ts` — the type and the function both moved here from the removed `assessmentFile.ts`) never throws: it calls `importYAMLFile` and reports the outcome via the exported **`ParseResult`** discriminated union (`{ ok: true, assessment, stateSchemaVersion } | { ok: false, error, forwardIncompatible? }`), so every caller (Assessments-tab upload, Comparison-panel baseline upload) branches on one shape regardless of whether the file parsed, was rejected as a JSON envelope, was malformed, or was forward-incompatible.
- **Deferred**: a signed/attestable export (the salted-digest `certification` profile the old JSON codec's envelope reserved a `profile` field for) remains a **future** format, not shipped. `canonicalize` (JCS, RFC 8785) is kept only as a **devDependency** — no longer a runtime dependency, since nothing in the shipped bundle calls it — solely to back `src/utils/signingFixture.test.ts`, a permanent fixture proving a JCS-canonicalize + detached `b64:false` ES256 JWS pipeline round-trips with the libraries (`canonicalize`, `jose`) a future signed export would use; it isn't wired into any current export/import path. Carrying the remaining v2 content over the URL share hash is also still deferred (unchanged from before): the hash carries `requirementProgress` level/applicability via the compressed `full` param, but the metadata scalars, `pkiEnvironment`, `workspace`, and `actionPlans` travel only in the YAML file.

### Maturity math (`src/utils/maturityCalculations.ts`)

This file is where the model gets non-trivial — read it carefully before changing scoring behavior.

- `getEffectiveWeight` applies category-level overlays (`override` > `multiplier` > `addition`).
- `getWeightSum` (private) sums requirement weights for a category, applying any per-requirement overlays from active extensions.
- `calculateBlendedLevel` is the key formula: blends a core category's level with the extension's relevance level using `(Level_C * WeightSum_C + RelLevel_C * RelWeight_C) / (WeightSum_C + RelWeight_C)`. Returns `-1` for explicit Not Applicable; returns the core level when the extension dimension is unrated; returns 0 when the core itself is unrated.
- `calculateOverallMaturityLevel` / `calculateModuleMaturityLevels` produce floored weighted averages. Not Assessed (level 0) and Not Applicable categories are **excluded** from the rollup, matching the framework spec.
- `calculateExtensionMaturityLevels` computes per-extension overall maturity using `effective_category_weight` per the [scoring spec](https://pkic.org/wg/pkimm/extensions/scoring/).
- `calculateExtensionFloorScore` returns the minimum blended level across applicable, assessed categories — only when `extension.floorScore === true`.
- `calculateExtensionWeightedPKIMMScore` uses baseline `Level_C` with extension-adjusted weights (NOT blended) per spec.
- `getCategoryOverlayInfo` returns a structured `CategoryOverlayDetails` shape (`{ category?, requirements[] }`); each entry carries `operation`, `value`, `base`, and `effective`. The Report tab and PDF render the same data side-by-side and stay in sync.
- 52 spec-anchored tests live in `maturityCalculations.test.ts` — when changing scoring math, run them and update them; they should keep tracking the published worked examples.

Scores are always `Math.floor()`-ed before display. `LevelResult` enum maps `-1 → "Not Applicable"`, `0 → "Not Assessed"`, `1–5 → "Initial"…"Optimized"`. In 2.0.0 the level-2 label is **"Foundational"** (renamed from "Basic"); the legacy `"2 - Basic"` string still appears in 1.0.0 fixtures and is rewritten on migration.

### Extensions and the AssessmentTargetContext

`AssessmentTargetContext` (`src/contexts/AssessmentTargetContext.tsx`) does **not** own progress — it only tracks which target is currently being viewed (`{ kind: 'original' }` vs `{ kind: 'extension', id }`). Components consume it to decide whether to render the baseline UI or extension-specific UI. Enabling an extension is independent of selecting it as the active target.

Each extension YAML has:

1. **`extension`** — id, name, version, description, optional `documentation`, optional `compatibility: string[]` (compatible model versions), optional `floorScore`.
2. **`relevance.modules[].categories[]`** — categories the extension cares about, with its own `weight`, `levels`, `guidance`, `assessment`, `references`.
3. **`overlays.modules[].categories[]`** (optional) — modifiers (`type: multiplier | addition | override`) applied to the core category weight and/or its requirement weights.

The widget enforces `compatibility`: extensions whose array doesn't include the loaded model version are surfaced in the Extensions tab with a disabled toggle and an "incompatible" badge.

Extensions are **browser-managed, not host-configured.** The user uploads a `.yaml` extension in the Extensions tab and removes it there; there is no `extensionsUrl` attribute and B1 adds no network fetch (the file is read locally via `File.text()`). The store lives in IndexedDB under the `meta` key `"extensions"` — accessed through `StorageAdapter.listExtensions`/`saveExtension`/`deleteExtension` (`storageTypes.ts` + both adapters), mirroring the scope-template store exactly (no new object store, `DB_STRUCTURAL_VERSION` stays 1). Upload flows through the pure `parseExtensionFile(text)` (`src/utils/extensionUpload.ts`): `yamlParser` → reject if no `extension` block → reject a non-string `schemaVersion` (because `validateSchema` no-ops without it) → `validateSchema` (Ajv2020); it never throws, returning `{ ok: true, extension } | { ok: false, error }`. `saveExtension` upserts by `ext.extension.id`, so re-uploading a same-id extension **replaces** its definition (gated by a `window.confirm`) without touching any assessment's `progress` — the handlers call only the store + `refreshExtensions()`, never an assessment write, so an assessment that used the replaced extension is never broken (a version bump surfaces the usual per-extension MigrationBanner; a hidden extension's progress is preserved as before). `useInitialLoad` loads extensions from the store (not a URL) and exposes **`refreshExtensions()`**, which rebuilds `extensionsData`, `incompatibleExtensionIds` (via the pure `computeIncompatibleExtensionIds(exts, modelVersion)`), and `referencesLookup` (from a retained base catalog + the current stored extensions' local `references[]`, via the module-scope `buildReferencesLookup`) — so an uploaded extension's references resolve immediately, no reload. Removing the currently-selected extension resets `AssessmentTargetContext.target` to `{ kind: "original" }` first (mirroring the toggle-off guard) so no stale extension-mode UI survives. A future Slice B2 (optional user-initiated catalog) is deferred — B1 has no catalog and no default URL.

### References (`referencesUrl` attribute)

The load effect always builds a `Map<id, ReferenceEntry>` (`referencesLookup` state) from a `ReferencesCatalog`: the **bundled catalog** (`BUNDLED_REFERENCES_YAML`) by default, or the fetched+parsed catalog when the consumer sets `referencesUrl` (override). Any extension-local `references[]` block declared in an extension YAML is merged into the same map (later entries win on collisions). The map is then:

- Passed down to each `Category` component — when the user opens a core category, a "References (N)" `<details>` disclosure renders below the level cards. Each row: title (linked to URL), authority, region pills. Extension category cards do the same against the extension's local references.
- Collected per-PDF — `Assessment.tsx`'s `collectReferencedEntries(modules)` walks the rendered modules, deduplicates ids, looks up each, and passes the resolved array into `exportToPDF` / `exportExtensionPDF`. Both PDFs add a sorted **References** appendix page (title / authority / regions columns) between the report body and the final About page.

Graceful degradation:

- `referencesUrl` not set → the **bundled catalog** seeds the lookup, so references render by default (disclosures + PDF appendix present). Only if the resolved catalog were empty would the disclosure not render / the PDF appendix return `null`.
- A category cites an id that's missing from the catalog → silently filtered out; other references still render.

`RequirementData.references` and `ExtensionCategoryData.references` are typed as `string | string[]` to accommodate both the 1.0.0 markdown shape and the 2.0.0 id-array shape. Only the id-array shape is resolved against the catalog; the legacy markdown string is currently ignored by the disclosure.

### Full-assessment requirement questionnaire

The "full" view mode (per-category `view === "full"`, `ViewMode` from `src/components/Assessment/hooks/useViewMode.ts`) replaces a core category's self-declared level cards with a per-requirement questionnaire — `FullCategory` inside `src/components/Category/Category.tsx` routes to it instead of the self-view branch; extension relevance categories always keep the self-view rendering regardless of the active mode (in full view that card additionally gains category-grain Evidence + Workspace links — see "Extension category-grain richness" below).

- **`RequirementCard`** (`src/components/Category/RequirementCard.tsx`) renders one card per in-scope requirement: sequence badge (`#N of totalInScope`), description, weight, a status chip, collapsible **Guidance** and **Assessment criteria** `<details>` (markdown), a **References** disclosure resolved against `referencesLookup`, an applicability toggle with a "Reason for not applicable" textarea when off, a `role="radiogroup"` of level buttons (0–5, arrow-key roving tabindex), **Rationale / Notes** and **Evidence** auto-growing textareas, a **Flag**/**Flagged** toggle button (a `faFlag` icon in the flagged state), and a **Mark complete**/**Completed** toggle button (a `faCheck` icon in the completed state — both `aria-hidden`, active-state only, symmetric). The three free-text fields (Rationale/Notes, Evidence, and the not-applicable reason) each carry an example-text `placeholder` for guidance (hardcoded, generic per field; native attribute through `TextArea`). Keyboard entry while the card (not a text field) has focus: digits `0`–`5` set the level directly, `f`/`F` toggles flagged, `n`/`N`/`p`/`P` move to the next/previous card. Only `attachOpen`/`searchText` are local React state; writes go through the same `onFieldChange` (`pocId`/`artifactIds`/`interviewDate`). No `RequirementProgress`/`WorkspaceLinks`/`RequirementCardProps`/scoring/schema/storage/URL/dependency change; self view unaffected.

An empty filter (no text, no statuses) matches every card, so the filter is a no-op when the finder isn't in use. `n`/`p` keyboard navigation walks only the filter-visible cards (`visibleViews`, not the unfiltered `views`), so it never lands on a card that's hidden and thus has no ref to focus.

On load, an assessment with a saved `lastPosition` triggers a one-time restore (sets tab/view, scrolls/focuses the saved card) and a dismissible `ResumeToast` (`src/components/ResumeToast/ResumeToast.tsx`, auto-dismisses after 6 s) reading "Resumed at: {name}" (the requirement/category name via `resolveRequirementName` — no positional numbers) or "Resumed where you left off" as a generic fallback.

### Category-level not-applicable reason

A core category (or extension relevance category) toggled off — `progress[key].applicability === false` — shows a "Reason this category is not applicable" auto-growing textarea, in both the self-view card (`Category.tsx`) and the full-view card (`FullCategory` in the same file); it reads/writes `progress[key].applicabilityReason`, the same `ProgressData` field the requirement-level "Reason for not applicable" textarea already used (`src/utils/requirementProgress.ts`'s `RequirementProgress.applicabilityReason` is the separate, per-requirement counterpart). `src/utils/categoryProgress.ts` — mirroring `requirementProgress.ts`'s pattern — holds the pure reducers `computeNextCategoryApplicability` (toggles applicability, preserves every other field including any existing `applicabilityReason`) and `computeNextCategoryReason` (merges a new reason without touching the rest of the entry), so a scope toggle never silently drops a previously entered reason. The field is gated strictly on `!isApplicable`; in-scope categories render byte-identical to before this feature.

### Category notes (self-assessment mode)

A category in **self/quick view** shows an optional free-text **Notes** auto-growing textarea (below the category description/level cards), reading/writing the additive `ProgressData.notes?` field. It renders on **core self categories AND extension relevance cards** (both self and full view — extension cards always use the self-view rendering since they never route to `FullCategory`); core full view routes to `FullCategory` before this card, whose per-requirement Rationale/Notes cover that grain. Writes go through `computeNextCategoryNotes` (`src/utils/categoryProgress.ts`, spread-prev like `computeNextCategoryReason`) via a `handleCategoryNotes` handler threaded `Assessment → Module → Category` (same shape as `onCategoryReason`; `handleCategoryNotes` builds the core-or-extension key `${extensionId?}.${moduleId}.${categoryId}`). **Notes survive every `ProgressData` entry-rebuild path:** `handleLevelChange` now delegates to the pure `computeNextCategoryLevel` (byte-matches the old inline rebuild — `applicability` always, `applicabilityReason`/`notes`/`evidence`/`pocId`/`interviewDate`/`artifactIds` only when truthy/non-empty), and the import-merge engine (`mergeAssessment.ts` — `progressEmpty` treats a notes/evidence/workspace-only level-0 entry as non-empty, `resolveProgress` fill-gaps carries all category-grain fields) preserves it. Notes ride the YAML export automatically (the whole `progress` map is dumped) and print in the **self PDF report** (`DetailRow.notes` → `CoreReportDocument`); they are **not** encoded in the URL hash (progress compaction keeps only `{level, applicability}`). `stateSchemaVersion` stays 2 (additive/unversioned). Resetting the "Ratings" scope intentionally clears notes with the level.

### Extension category-grain richness (A+B)

Extension relevance categories have **no requirements** in the extension schema, so they carry free-text at **category grain** rather than per requirement. In **self view** an extension card shows **Notes** (above); in **full view** it additionally shows **Evidence** + **Workspace links** (POC / artifacts / interview date), gated `extCategory && view === "full" && isApplicable`. These live on the extension-keyed `ProgressData` entry (`${extId}.${moduleId}.${categoryId}`) via the additive optional fields `evidence?`/`pocId?`/`interviewDate?`/`artifactIds?` (same names `RequirementProgress` uses). Writes flow through one generalized reducer + handler — **`computeNextCategoryField<K extends CategoryEditableField>`** (`categoryProgress.ts`, `CategoryEditableField = "evidence" | "pocId" | "interviewDate" | "artifactIds"`) and **`handleCategoryFieldChange`** in `Assessment.tsx` (mirrors `onRequirementFieldChange`), threaded `Assessment → Module → Category` as `onCategoryFieldChange`. The shared **`WorkspaceLinksSection`** is grain-agnostic: it reads a minimal `links: { pocId?, artifactIds?, interviewDate? }` (a structural subset of both `RequirementProgress` and `ProgressData`) and takes an `idPrefix` for aria ids; `RequirementCard` passes `links={progress}` + its existing `onFieldChange` (byte-identical requirement behavior), while the extension card passes `links={categoryProgress}` + an `onCategoryFieldChange`-bound adapter. The extension **PDF report** (`ExtensionReportDocument` Relevance Details, rendered through the shared `Table` + `TableTextRow`) shows per-relevance-category **Notes + Evidence** (not workspace links — matching the core Detailed report); `RelevanceRow.notes`/`.evidence` come from `buildRelevanceRows` reading `progress[extKey]`. All four fields ride YAML export, are dropped from the URL hash (like core notes), survive migration (migrate copies the whole entry) and import-merge, and keep `stateSchemaVersion` at 2. No scoring/schema/URL change; core self/full cards render byte-identical.

- **ImportCollisionModal** (`src/components/ImportCollisionModal/`) is a focus-trapped `role="dialog"` comparing `meta.updatedAt` on both copies ("The file is newer/older than your local copy by N days", or "about the same age" for a same-day tie) with three actions: **Replace** snapshots the existing local copy as a `pre-import` revision (visible afterward in History) via `adapter.snapshotRevision(existing, "pre-import")`, then writes the incoming record with `meta.updatedAt` bumped to "now" — the bump is required so the merge-on-write stored-newer-wins guard in `writeSavedState` can't silently drop an imported file that happens to be older than the local copy, defeating the user's explicit choice (mirrors how `restoreRevision` bumps `updatedAt` before its own write). **Keep both** mints a fresh id via `newId()`, appends `" (imported)"` to the name, and sets `meta.importedFromId` to the original id (the existing provenance field also used by Duplicate), adding it as a new, separate assessment. **Cancel** makes no change. **Merge** (fourth action, shown only when `existing.dataVersion === incoming.dataVersion` via the `canMerge` prop; otherwise a "different model version" note) field-level-merges the incoming file into the existing record using one user-picked deterministic strategy from a `<select>` — `fill-gaps` (never overwrites non-empty existing content; the "decision" fields `applicability`/`applicabilityReason`/`ActionPlanEntry.targetLevel` are never gap-filled), `prefer-newest` (per-requirement `RequirementProgress.updatedAt`, falling back to whole-assessment `meta.updatedAt`), or `prefer-imported`. The merge is always a **key-union** (no strategy drops an existing-only key). The pure engine `mergeAssessments(existing, incoming, strategy)` (`src/utils/mergeAssessment.ts`) is deterministic (no clock — `Date.parse` only) and keeps `existing`'s `id`/`dataVersion`/`sourceStructure`/`lastView`/`lastPosition` and `meta.importedFromId` (a merge keeps the record's identity), with `meta.createdAt` = the earlier of the two; `handleImportMerge` snapshots a new `"pre-merge"` `RevisionReason` (additive; `snapshotRevision`/`putRevision` don't branch on reason) before writing the merged record (same id, `meta.updatedAt` bumped to "now"). No scoring/schema/URL/dependency change; same-`dataVersion` only. A same-id import that ISN'T currently loaded locally (no collision) still gets its `meta.updatedAt` bumped to "now" before being added — this defeats the 90-day tombstone guard in the same way, so re-importing a file whose id this browser previously deleted is treated as a legitimate new write rather than silently dropped. Deleting an assessment and immediately re-importing an export with the same id inside the same 300 ms debounce window is handled by `unmarkDeleted` on `useTabPersistence` — it reverses a still-pending, not-yet-flushed delete for that id so the queued `deleteIds` can't ride along on the next write and undo the reimport. The tombstone comparison itself is a strict `>` (`tomb > updatedAt`, not `>=`): a same-millisecond tie between a delete and an immediately-bumped reimport favors the incoming write, since `toISOString()` only has millisecond resolution and a genuinely stale flush is still caught (its stored `updatedAt` predates the tombstone strictly).

A `SectionComponent = (ctx: SectionContext) => ReactElement | null` is deliberately typed as a plain function, not `React.FC` — React 19's `FC` also permits an async/ReactNode return, which would defeat the synchronous null-filtering `ReportDocument` depends on to decide page breaks before it renders anything. Only `cover` (`Cover.tsx`) returns its own `<Page>`; every other section returns flowing content or `null`. `SectionContext` (`SectionContext.ts`) is the one prop bag every section reads from — identity/timing scalars, the `reportData`/`distribution`/`exclusions`/`coverage`/`reportCompleteness`/`requirementDetailRows`/`gapRows`/`actionPlanRows`/`comparison`/`reconciliationRows` builder outputs, `pkiEnvironment`, `references`, and the raw `modules`/`progress`/`requirementProgress` — built once by the dispatcher and passed unchanged to every picked section. The three full-tier presets are additive ordered subsequences of `SECTION_ORDER` — `ATTESTATION_SECTIONS ⊂ ASSESSMENT_SECTIONS ⊂ DETAILED_SECTIONS` (pinned by a registry test) — and `resolveSections(tier, custom?)` returns a named tier's preset array, or — for `tier: "custom"` — `SECTION_ORDER` filtered down to a caller-picked `SectionKey[]` (unknown/duplicate keys silently ignored/deduped). `PAGE_BREAK_BEFORE` (a `Set` containing `maturityCharts`, `references`, `requirementDetails`, `gapToNext`, `actionPlans`, `comparison`, and `about`) marks the sections that start on a fresh `<Page>` (see `ReportDocument` below — these are real page boundaries, not `break` views). `maturityCharts` is in the set for a second reason beyond length: its radar `<Image>` must never sit inside a group that relocates across a page boundary (the v4.5.1 image bug below).
- **`ReportDocument`** (`src/utils/pdf/ReportDocument.tsx`) is the single renderer every tier and every Custom pick goes through: one ordered `SectionKey[]` against one `SectionContext`, producing the Cover's own `<Page>` (only when `cover` is in the set) followed by **page groups** — the post-null-filter rendered body sections are partitioned so each `PAGE_BREAK_BEFORE` section starts a new group, and each group renders as its own `<Page size="A4" wrap>` with the shared fixed `Header`/`Footer` (page numbers are document-global via `render={({ pageNumber, totalPages }) …}`, so numbering is seamless across groups). There are **no `break` views anywhere** — a `break` prop on a section whose preceding content happens to end exactly at a page boundary emits a spurious blank page in `@react-pdf` v4.5.1 (data-dependent, caught by the rendered-quality audit); genuinely separate `<Page>` elements are the only deterministic fresh-page tool. A picked set whose body sections all render `null` (or whose only pick is `cover`) emits no body pages at all. Spacing is decided here too: within a group, every rendered section after the group's first gets `SECTION_GAP` (16, `theme.ts`) as a `marginTop` wrapper; a group's first section starts flush under the page header — a section must never carry its own section-root top margin, or it would double up with this one.

- **PDF rendering-defect fixes underpin every tier.** Roboto is registered from locally-bundled matched Regular + Bold TTFs (`src/assets/fonts/Roboto-{Regular,Bold}.ttf`, `theme.ts`'s `Font.register` — no network fetch, no fake-bold synthesis), fixing fontkit's leading-glyph drop on bold text runs that a fake-bold/cold-cache race used to cause. `theme.ts`'s `cssVar(name, fallback)` guards every `--pkimm-*` lookup behind `typeof document === "undefined"` so the module stays import-safe in a node test/SSR context, falling back to the fixed default instead of throwing. The shared **`Table`** primitive (`src/utils/pdf/Table.tsx`) uses **row-owned borders** — every `TableRow` draws its own left/right/bottom edge and the header row (or an injected `isFirst` on the first body row when there's no header) draws the top — never a border on the table container: a container border leaves an empty bordered sliver on the page where a table splits at a row boundary. **Multi-column rows are ALWAYS atomic** (`TableRow` has no `wrap` prop at all): a breakable flex-row splits MID-row at a page boundary, rendering its continuation with empty left cells and slicing pills. Unbounded user text therefore never renders in a table column — callers compare against **`LONG_TEXT_CHARS` (280) / `isLongText(…)`** and, when long, emit a compact atomic meta row followed by a **`TableTextRow`** (the one breakable row: a single full-width text cell with an optional bold `label` lead — one column cannot misalign on a split; emitted as an array sibling, never inside a Fragment, since `Table` inspects direct children). This adaptive pattern runs in `ScopeOverview` (reasons), `RequirementDetails` (notes/evidence, with the meta row keeping header column positions via an empty 48% cell), `PkiEnvironmentTable` (values under a full-width field-label row), and `GapToNext` (criteria). `Table` also takes a **`leadIn`** slot — content (category/module headings, as plain `<Text>`, never `SectionHeading`) glued into the same `wrap={false}` group as the header and first atomic row, so a heading can never strand above a table that moved on. The header glue is skipped when the first row is a `TableTextRow` (unbounded height). `CompletenessRings` (`src/utils/pdf/charts/CompletenessRings.tsx`) centers its per-module rings and draws a full/empty ring with butt caps (round caps only for a genuine partial arc) so the ends meet seamlessly instead of overlapping at 12 o'clock. PKI Environment renders as a sized Field|Value **table** (`PkiEnvironmentTable.tsx`, Assessment/Detailed tiers) rather than loose paragraphs, with `TableRow wrap` so a long free-text value is never clipped. **No orphan headings:** `SectionHeading` (`src/utils/pdf/SectionHeading.tsx`) wraps every section (and sub-section) heading with a `minPresenceAhead` node prop (`HEADING_RESERVE` 60 default, `SUBHEADING_RESERVE` 40 for lighter sub-heads) — but `minPresenceAhead` is empirically **unreliable** in v4.5.1 (doesn't fire when nested, sometimes not even on direct Page children), so it is best-effort only; the deterministic tools are `PAGE_BREAK_BEFORE` fresh pages plus the rendered-quality audit (below), which asserts no heading strands at a page bottom. Every section that used to spell its heading as a raw styled `<Text>` (`GapToNext`, `RequirementDetails` and its sub-headings, `ComparisonToBaseline`'s sub-headings) now renders through `SectionHeading` instead. **Glyph-safe text is a hard rule across every PDF section:** the embedded Roboto subset silently mis-maps the `→` arrow, `−` math-minus, `▲`/`▼` triangle, and `✓` check glyphs, so no section spells any of them in a `<Text>` run — `GapToNext` spells "Current"/"Next"/"to" as words instead of an arrow; `ActionPlans`' `ProgressionArrow` and the comparison's `DeltaIndicator`/`DeltaTriangle` (`DeltaIndicator.tsx`) draw arrows/direction as a small `@react-pdf` `Svg`/`Polygon` triangle rather than a `→`/`▲`/`▼` glyph, and a negative delta's leading `-` is the plain ASCII hyphen from template-literal interpolation, never the `−` minus-sign glyph; `ActionPlans`' `TaskStatusBox` stands in for a checklist item's done state with a filled/empty box, never a `✓` glyph; `—` em dash, `–` en dash, `•` bullet, and `×` times remain safe and are used throughout.
- **Generation-time validation + rendered-quality audit.** `validateReportComposition(sections)` (`src/utils/pdf/validateComposition.ts`) structurally checks a composition — non-empty, only known `SectionKey`s, no duplicates, strictly canonical `SECTION_ORDER` order, cover-first, about-last — and the throwing `assertValidReportComposition` is called by `exportToPDF` right after `resolveSections`, so a malformed composition fails fast instead of shipping a broken PDF. Its executable counterpart is the permanent **rendered-quality audit** (`src/utils/pdf/reportQuality.render.test.tsx`): every tier preset × {empty, partial, full, **long**} fixtures plus a mixed Custom pick renders through the REAL `@react-pdf` pipeline — `longFixture` (`src/test-utils/reportFixtures.ts`) is the abuse fixture, every user-controlled free-text field pushed to multi-thousand-character lengths, proving the layout survives arbitrary input — and `renderPdfPageItems` (`src/test-utils/pdfText.ts`, a pdf-parse `pagerender` hook returning per-page positioned text items `{str, x, y}` — PDF user space, origin bottom-left, footer band below `y≈45`) backs five invariants per page: no blank/sparse page (≥25 content chars above the footer), the cover page actually contains the report title, no heading stranded at a page bottom with nothing below it (named headings plus the `/^[A-Z]{1,2} — /` module-heading pattern), no forbidden glyph (`→ ▲ ▼ ✓ −`), and **no overlapping text** (two multi-word runs at the same x within ~3pt of the same baseline — the signature of the v4.5.1 zero-height content collapse). This audit has caught multiple real bugs before any human saw them; run it whenever touching PDF sections. **Four `@react-pdf` v4.5.1 pagination behaviors it guards against** (all empirically bisected): (1) a `break` prop on content whose predecessor ends exactly at a page boundary emits a spurious blank page — hence `ReportDocument`'s page-group architecture with no `break` views; (2) a `wrap={false}` group containing an `<Image>` that must relocate to the next page corrupts ALL following content — hence `maturityCharts` is in `PAGE_BREAK_BEFORE` and its radar `<Image>` is a plain sibling, never inside a `wrap={false}` group; (3) **a breakable (wrap) subtree that fits within one page RELOCATES wholesale instead of splitting** — a near-page-height wrapper View (a whole plan card, a whole module of tables) jumps to the next page stranding whatever preceded it, so no wrapper View may enclose near-page-height content (ActionPlans cards are flat sibling pieces; RequirementDetails has no module wrapper); (4) **relocating a breakable wrapper that contains a `wrap={false}` header-glue group can CRUSH its content into zero-height overlapping rows at the page bottom** — so content takes only the two proven-clean paths: directly-atomic blocks (small requirement categories ≤12 short rows, GapToNext category blocks) or taller-than-page flowing content that splits. Also `minPresenceAhead` is unreliable (see the orphan-headings note above) and `strokeDashoffset` is unsupported (rings use `strokeDasharray` + a `rotate(-90)` `<G>`).

## Host theming

The widget is intentionally generic so it can ship into any host page. Hosts theme it by overriding `--pkimm-*` custom properties in their own CSS. Defaults are deliberately neutral; pick what you want to override.

Tokens worth overriding for brand alignment:

| Token                                                                                                         | What it controls                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `--pkimm-font-family`                                                                                         | Whole widget's font stack (Roboto first by default)                                                                                             |
| `--pkimm-primary-color`, `--pkimm-primary-color-hover`, `--pkimm-primary-color-lighter`                       | Brand colour for buttons, tabs, active rows, progress bars                                                                                      |
| `--pkimm-secondary-color`                                                                                     | Extension accent (badges, `ext` tag)                                                                                                            |
| `--pkimm-text-color-dark`, `--pkimm-text-color-muted`, `--pkimm-text-color-light`                             | Body / caption / on-primary text                                                                                                                |
| `--pkimm-background-color`, `--pkimm-surface-color`, `--pkimm-surface-color-alt`                              | Page bg / card bg / alt input fill                                                                                                              |
| `--pkimm-border-color`, `--pkimm-border-radius-{sm,md,lg,badge,pill}`                                         | Card/row borders + radii                                                                                                                        |
| `--pkimm-shadow-sm`, `--pkimm-shadow-md`, `--pkimm-shadow-header`                                             | Card / dropdown / sticky-header elevation                                                                                                       |
| `--pkimm-header-height`                                                                                       | Sticky main-header height (default 110px); offsets the sticky chart panel + tab-content scroll clearance — raise it if your header wraps taller |
| `--pkimm-banner-{bg,border,fg}`, `--pkimm-success-{bg,border,fg}`, `--pkimm-danger-{bg,border,fg}`            | Notice/banner/badge semantics                                                                                                                   |
| `--pkimm-overlay-color`                                                                                       | Modal overlay                                                                                                                                   |
| `--pkimm-hover-bg(-subtle)`, `--pkimm-hover-bg-extension(-subtle)`                                            | Interactive hover surfaces                                                                                                                      |
| `--pkimm-table-stripe-bg`, `--pkimm-table-row-hover-bg`, `--pkimm-table-header-bg`, `--pkimm-table-header-fg` | Report table look                                                                                                                               |
| `--pkimm-maturity-level-{1,2,3,4,5}`                                                                          | Per-level chart and badge colours                                                                                                               |

Example — making the widget look native on **pkic.org** (Bootstrap-based, green primary, Roboto, dark table headers):

```css
self-assessment {
  --pkimm-primary-color: rgb(25, 135, 84);
  --pkimm-primary-color-hover: rgb(20, 108, 67);
  --pkimm-primary-color-lighter: rgb(212, 237, 218);
  --pkimm-secondary-color: rgb(255, 192, 0);
  --pkimm-table-header-bg: rgb(33, 37, 41);
  --pkimm-table-header-fg: #fff;

```

(The font stays Roboto without any override because the widget's default stack already lists Roboto first; pkic.org bundles Roboto, so the widget picks it up automatically.)

## Shared UI primitives (`src/components/ui/`)

A shared, host-themeable React primitive library is the single source of truth for interactive/visual chrome — **use these instead of hand-rolling buttons/toggles/fields/cards/dialogs** in any tab or component. Each lives at `src/components/ui/<Name>/<Name>.tsx` + `<Name>.module.scss` + `<Name>.dom.test.tsx`, re-exported from the `src/components/ui/index.ts` barrel, styled ONLY via `--pkimm-*` tokens (so host theming keeps working), un-hashed `pkimm-`-prefixed classes, with per-component jest-axe tests.

- **`Button`** (`variant: primary|secondary|danger|ghost`, `size: sm|md`, `leftIcon`; **defaults `type="button"`**) + **`IconButton`** (`label`→`aria-label`). Canonical source promoted from the Report/AssessmentManager button systems.
- **`Toggle`** (`checked`/`onChange`/`label`, `size`, `accent: primary|secondary`) — the on/off switch (promoted out of `Category.module.scss`; the `pkimm-toggle-switch`/`pkimm-slider` classes now live here). **Accent is per-consumer to match prior rendering: Category extension-relevance cards pass `accent="secondary"`; `Extensions.tsx` uses the default `primary`.**
- **`Checkbox`** (tri-state, forwards `ref` to the `<input>`) — for the Scope tree's indeterminate checkboxes. `CheckboxProps` is a discriminated union requiring exactly one of **`label`** (renders as `aria-label`) or **`labelledBy`** (renders as `aria-labelledby`, pointing at an existing id) — never both — so a checkbox next to visible text (e.g. the Scope tree's category/requirement/module names) can be named by that text instead of duplicating it in an `aria-label`. The `.pkimm-checkbox` box itself is sized off the spacing scale (`calc(--pkimm-space-md + --pkimm-space-2xs)`, not a hardcoded px value) and its checked/indeterminate marks are drawn with **percentage** dimensions relative to that box (not fixed px), so the whole control scales cleanly if the underlying tokens change.
- **`TextField` / `TextArea` (`autoGrow`, `onInput`-only, no mount sizing) / `Select`** — shared form-field chrome (`.pkimm-field`), promoted from Report's inputs. `TextField`/`TextArea` also take an optional **`hint?: string`** that renders a `.pkimm-field__hint` span wired to the control via `aria-describedby` (composed after `...rest`, preserving any caller `aria-describedby`); because a hint span inside the implicit-label wrapper would otherwise fold into the control's accessible name, the primitive pins the accessible name to `label` via `aria-label` whenever a `hint` is present (byte-identical when `hint` is omitted). They require a `label` string prop (always rendered as the field's real `<label>` text for assistive tech) plus an optional **`hideLabel?: boolean`** that visually hides that label span via the `.pkimm-visually-hidden` utility class while keeping it in the accessibility tree — for repeated-row layouts (e.g. Workspace's per-artifact/POC/intake rows, Action plans' per-plan target-level `<select>`) where a visible label would just repeat context already shown once at the section level, but each row still needs its own unique accessible name (e.g. `` `Artifact title ${a.id}` ``). `TextField` and `Select` also take an optional **`fieldClassName?: string`**, applied to the outer `.pkimm-field` `<label>` wrapper (as an additional class, never replacing `pkimm-field`) — feature code uses it to attach a small `max-width` rule so a compact control (e.g. a per-plan target-level `<select>`, a template-name field) doesn't stretch to fill a wide flex/grid cell; `TextArea` has no such prop since its width is always driven by its container. The shared `.pkimm-field__control` rule (`src/components/ui/field.module.scss`) is the sizing contract every text input/textarea/select shares: `box-sizing: border-box`, `width: 100%`, `max-width: 100%`, `min-width: 0` (so a control never overflows a shrinking flex/grid cell), plus `resize: vertical` and a `min-height` for `<textarea>`. Primitives own this control-level sizing; feature `.module.scss` files only ever add layout — a `max-width` cap via `fieldClassName`, grid/flex placement — never box-sizing/width overrides on `.pkimm-field__control` itself.
- **`Card`** (`as: div|section|article`, `padding: none|sm|md|lg` ≤24px, `elevated`) — the shared surface recipe: border + `--pkimm-border-radius-lg` + `--pkimm-shadow-sm` on every `Card` (matching `.pkimm-chart-container`'s recipe), `--pkimm-shadow-md` when `elevated`. `as` picks the rendered tag (`"section"` lets a `Card` double as a labelled landmark via `aria-labelledby` — used by Scope's per-module cards and every Workspace/Evaluation section); `padding="none"` omits the padding class entirely (Scope's module card supplies its own internal spacing). Every full-assessment tab is built from `Card`s on the plain background — no separate outer tab-frame class: `Overview` and the Report tab each render their whole content as a single `Card`; Scope/Workspace/Action-plans/Evaluation render their content as one or more section `Card`s. This keeps borders/shadows identical across every tab.
- **`LevelBadge`** (`level: -1..5`, `variant: solid|soft|text`) — colour-codes a maturity level via `--pkimm-maturity-level-N` + the `LevelResult` label (replaces ad-hoc uncoloured level text).
- **`StatusPill`** (`tone: success|warning|neutral`, extends button attrs) — a themed `<button>` pill carrying a visible text label (children) + colour, for scope in/partial/out state. Used by the Scope tab's accordion in place of checkboxes; the consumer supplies the visible label plus a `.pkimm-visually-hidden` name/action span so the accessible name contains the visible text (WCAG 2.5.3). Tones map to `--pkimm-success-*` / `--pkimm-timing-warning-*` / neutral surface tokens.
- **`Banner`** (`tone: info|success|danger`, `title`, `onDismiss?`, `className?`) — the one-off notices (LegacyImportPrompt / TransientAssessmentBanner / MigrationBanner / hidden-extension / assessment-in-progress).
- **`Modal`** (`open`, `onClose?`, `dismissable?` default true, `title?`/`titleId?`, `initialFocusRef?`, `placement?: "center" | "right"` default `"center"`) — the shared focus-trap + overlay + Escape shell (promoted from ImportCollisionModal). Renders **no chrome of its own** (callers own headings/content). Pass `titleId` (the body's existing `<h2 id>`) — NOT `title` — to name the `role="dialog"` node without rendering a duplicate heading. `ReportGeneratingModal` uses `dismissable={false}` (Escape/overlay no-op). **`MigrationSummary` is intentionally NOT on `Modal`** — it is a bare `<dialog>` with no focus-trap today, so folding it in would change behavior (a future decision, not part of the primitive adoption). **`placement="right"`** is additive — every existing consumer keeps the byte-identical centered dialog via the default — and renders a right-anchored drawer (`.pkimm-modal-overlay--right`/`.pkimm-modal--right`) instead; the Help drawer (below) is its first and, so far, only consumer.
- **`Menu`** (`label`, `items: MenuItem[]`, `align?: "start" | "end"`) — the shared overflow/action menu (the single ⋮-menu pattern). Trigger is a ghost `IconButton` (`faEllipsisVertical`, `aria-haspopup="menu"`/`aria-expanded`); the popover is a `role="menu"` list of `role="menuitem"` buttons. Keyboard: ArrowUp/Down (wrapping) + Home/End move focus, Enter/Space activate, Escape closes and refocuses the trigger, Tab closes; focus moves to the first item on open; a pointerdown outside closes. Each `MenuItem` is `{ id, label, icon?, tone?: "default" | "danger", onSelect }` — a `danger` item is `--pkimm-danger-fg`. Because `IconButton` does not forward a ref, the menu refocuses its trigger via `querySelector('[aria-haspopup="menu"]')` inside its own root. Consumers: the Assessments-tab cards and `FullCategory`'s sticky sub-header (the "Clear requirement assessments" overflow — `Category.tsx`'s formerly-bespoke ⋮ menu now uses this primitive). `Category.tsx`'s self-view card has no ⋮ menu.
- Tokens: a spacing scale `--pkimm-space-3xs … --pkimm-space-2xl` (in `src/index.module.scss`) replaces ad-hoc px/rem.
- **`.pkimm-visually-hidden`** (`src/index.module.scss`) — the standard clip-to-1px-offscreen utility class (position absolute, 1px box, clipped, no reflow) for content that must stay in the accessibility tree without being visible; this is the class `TextField`/`Select`'s `hideLabel` applies to the label `<span>`, and it's available for any other component that needs the same treatment.

## Conventions & gotchas

- **CSS class names are NOT hashed.** Webpack uses `localIdentName: "[local]"` for `.module.scss` files. The `pkimm-` prefix is what prevents host-page collisions — use it for any new class. CSS variables exposed to hosts must be added in `src/index.module.scss`. **Shared interactive/visual chrome comes from `src/components/ui/` primitives (above) — don't re-hand-roll buttons/toggles/fields/cards/dialogs; the toggle-switch and shared button/field/card classes moved out of individual tab `.module.scss` files into `ui/`.**
- **Feature SCSS never re-styles primitive chrome — only layout.** A feature `.module.scss` file (Scope, Workspace, Action plans, Report, Comparison, Evaluation, etc.) never overrides `Button`/`Card`/`.pkimm-field__control`/`.pkimm-checkbox`'s own colour/border/padding/sizing — it only adds layout around them: grid/flex placement, gaps, and (via `TextField`/`Select`'s `fieldClassName`) a `max-width` cap on the outer `.pkimm-field` wrapper for a compact control. Nearly every text input, `<select>`, and checkbox in the full-assessment surfaces (Scope, Workspace, Action plans, Report filters, Comparison's assessment picker, per-requirement workspace links, etc.) is one of the shared primitives. A few controls are deliberately still raw `<input>` elements, by design, not oversight: the Comparison panel's `<input type="file">` and the Scope tab's template-import `<input type="file">` (native file pickers aren't themed) and `RequirementFinder`'s search `<input>` (a bespoke inline search box, not a labelled field). Don't read the primitive adoption as "no raw inputs remain" — these are intentional exceptions.
- **`src/version.ts` imports `package.json`.** The bundle includes the version string at build time and renders it in the spider-chart corner. Bumping `package.json#version` is the only step needed to roll the displayed version.
- **`WIDGET_MAX_STATE_SCHEMA_VERSION` is defined in `src/utils/stateSchema.ts`** only. It caps the forward-compat check; bumping it is a breaking change (old widgets will refuse newer saves).
- **Extension support is unified, not separate components.** There are no `ExtensionAssessment`/`ExtensionReport`/`ExtensionsView` components (earlier empty placeholder dirs were removed) — extension assessment/report/list support lives inside the unified `Assessment`, `Module`, `Category`, `Report` components, routed by `AssessmentTargetContext`. Extend the unified components rather than reintroducing parallel ones.
- **Two jest projects (`jest.config.js` uses `projects`).** The default **`node`** project runs pure logic tests (`*.test.ts(x)`, `testEnvironment: node`) — keep these DOM-free, as most of the codebase's tests are. A second **`dom`** project runs `*.dom.test.tsx` under `jest-environment-jsdom` + React Testing Library, for hook/component tests via `renderHook` (`jest.setup.dom.ts` loads `@testing-library/jest-dom` and registers the `jest-axe` matcher via `jest-axe/extend-expect`; a `moduleNameMapper` stubs `*.scss`). `npm test` runs both. Prefer a pure node test when the unit has no React/DOM; use a `.dom.test.tsx` only for hooks/components. Tests live next to the unit they test (`src/utils/*.test.ts`, `src/legacy/*.test.ts`, `src/components/**/hooks/*.dom.test.tsx`). IndexedDB tests use `fake-indexeddb` (fresh `IDBFactory` per test); `navigator` stubbing in node tests must use `Object.defineProperty` (plain assignment throws on modern Node). Do not name a local variable `module` in a `.dom.test.tsx` — ts-jest compiles to CommonJS and that identifier shadows the module wrapper's own `module` binding, corrupting `module.exports` (surfaces as a `ReferenceError: exports is not defined` pointing at an unrelated line).
- **Accessibility baseline (§6.9, WCAG 2.1 AA).** `src/components/Category/RequirementCard.a11y.dom.test.tsx` is the jest-axe capstone: it renders the full-view `Category` (a couple of requirements, one Not Applicable) plus the `RequirementFinder` and asserts `expect(await axe(container)).toHaveNoViolations()` — run it whenever touching questionnaire markup. The sticky sub-header level/count (`Category.tsx`) and the right-rail overall/per-module readouts (`Assessment.tsx`) live inside `aria-live="polite"` regions so screen readers announce recalcs without needing to re-poll. Tab switches move focus to the `pkimm-categories-container` panel (`Assessment.tsx`'s `panelRef`) except when a session-resume restore is in flight, which keeps its own focus target (the restored requirement card). Every toggle-switch `<input type="checkbox">` (category/requirement applicability) carries an explicit `aria-label` — axe's `label` rule flags these because the `<span class="pkimm-slider">` sibling has no text.
- **ESLint uses flat config** (`eslint.config.mjs`) and ignores `dist/`. Custom rules: `semi: error`, `prefer-const: error`, `@typescript-eslint/no-unused-vars` with `argsIgnorePattern: ^_`.
- **PDF export trick:** `handleExportPDF`/`handleExportExtensionPDF` temporarily override `chartExtensionsOverride` and disable chart animation, wait for a paint, then capture the canvas. Don't remove the `setTimeout(100)` without verifying the chart canvas is fully painted.
- **Schemas stay build-time only.** The JSON schemas are imported by `yamlParser.ts` and inlined into the bundle. They're not copied into `dist/` — the pkimm repo is the canonical public source.
- **Outbound pkic.org links must be absolute and point to canonical, version-agnostic entry points.** The widget is embedded on arbitrary host pages, so a relative `/wg/...` would resolve against the host domain — always use full `https://pkic.org/...` URLs (see `Overview/overviewContent.ts` `RESOURCES` and `pdf/StaticPages.tsx`). Use only roots pkic.org keeps stable across model releases: `/wg/pkimm/model/` (current model — rolling "latest"), `/wg/pkimm/model/categories/`, `/wg/pkimm/model/assessment/`, `/wg/pkimm/extensions/`, and `/wg/pkimm/assessment/` (this widget's own landing). Do **not** hardcode a frozen version path (e.g. `/wg/pkimm/1.0.0/…`) or a non-existent one — `/wg/pkimm/categories/` and `/wg/pkimm/tools/` are **not** real paths. And never point at a mutable branch raw URL (`raw.githubusercontent.com/.../main/…`); bundle any needed data at build time.

## CI / deployment

- **PRs → main**: `check_build.yml` (build sanity), `check_linting.yml`, `check_formatting.yml`, `test.yml`. Use `NODE_OPTIONS=--max_old_space_size=4096` for `npm run build` to match CI memory budget.
- **Push to main**: `deploy_gh_pages.yml` builds and copies `index.html` and the three runtime YAMLs (`pkimm-model-1.0.0.yaml`, `pkimm-model-2.0.0.yaml`, `pkimm-references.yaml`) from `src/public/` into `dist/`, then publishes to the `gh-pages` branch under `develop/` — served at `pkic.github.io/self-assessment/develop/`.
- **Push tag (`*`)**: `release.yml` does the same, publishing under `gh-pages/<tag>/` — served at `pkic.github.io/self-assessment/<tag>/`.
- **GitHub Release published**: `release-package.yml` publishes the npm package `@pkic/self-assessment` to GitHub Packages (`npm.pkg.github.com`).
